# ADR 0001: минимальный каркас и тестовая БД

Статус: принято для этапа каркаса. Дата: 16 ноября 2026 года.

## Решение

Один Rust workspace содержит `crates/api`, пакет `flo-api`. API построен на Axum, SQLx и SQLite. Веб и нативный Android используют один контракт. Расчётный модуль, аккаунты и партнёрский доступ на этом этапе не реализуются.

SQLite выбран для тестового сценария: БД хранится в одном файле, не требует отдельного процесса и подходит для запуска на компьютере и сервере пользователя. Это предварительное решение для каркаса; пригодность SQLite для дальнейшей нагрузки и синхронизации оценивается отдельно. SQLx выполняет обращения асинхронно, пул ограничен пятью соединениями, время ожидания — пять секунд. Включены WAL и проверка внешних ключей.

## Запуск и хранение

Из корня репозитория: `cargo run -p flo-api --locked`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BIND_ADDR` | `127.0.0.1:8080` | Адрес HTTP-сервера |
| `DATABASE_URL` | `sqlite://.data/flo.db` | Файл SQLite; относительный путь отсчитывается от рабочей директории |

Родительская папка файла БД создаётся при запуске. Миграции встроены в бинарный файл и применяются SQLx один раз с контролем версий. Первая миграция создаёт `demo_messages` с единственной строкой `id = 1`, `message = 'Привет из SQLite'`. Последующие старты не заменяют изменённый текст. Для изменения сообщения в тестовом окружении можно выполнить SQL `UPDATE demo_messages SET message = 'Новый тестовый текст' WHERE id = 1;`.

БД и её WAL/SHM-файлы не включаются в Git. В БД каркаса хранится только синтетический текст. Пул закрывается после завершения активных запросов при Ctrl+C или SIGTERM.

## Контракт HTTP

### GET /api/message

Успех, HTTP 200, `Content-Type: application/json`, `Cache-Control: no-store`:

```json
{"message":"Привет из SQLite","source":"sqlite"}
```

Поле `message` читается из SQLite при каждом запросе. Изменение текста в БД становится видно после следующего запроса клиента без пересборки приложения.

Если строка отсутствует: HTTP 404, `{"error":"demo_message_not_found"}`. При недоступной БД или ошибке запроса: HTTP 503, `{"error":"database_unavailable"}`. SQL, путь к файлу и содержимое БД в HTTP-ошибки не включаются.

### GET /health

Проверяет подключение к БД запросом `SELECT 1`. Успех: HTTP 200, `{"status":"ok","database":"ok"}`. Ошибка: HTTP 503, `{"error":"database_unavailable"}`. Проверка не подтверждает наличие демонстрационной строки: её наличие проверяется через `/api/message`.

Неизвестный маршрут возвращает HTTP 404, `{"error":"not_found"}`. Неподдерживаемые методы стандартно получают HTTP 405.

## Доступ и ограничения

Авторизации пока нет: маршруты открыты и предназначены только для тестового текста. По умолчанию сервер слушает loopback. Для реального дневника, аккаунтов и партнёрского просмотра перед расширением доступа обязательны отдельная модель полномочий и защита данных.

Разрешающий CORS не включён. Веб-разработка использует same-origin прокси Vite, серверная установка — reverse proxy для `/api` и `/health`. Android не ограничен браузерным CORS. Удалённый публичный запуск и TLS в текущий этап не входят.

## Проверки

Интеграционные тесты используют временные файлы SQLite. Проверяются начальный ответ, чтение изменённого значения, сохранение изменения после повторного открытия БД, отсутствие жёстко заданной подстановки при удалённой строке и отражение недоступности БД в `/health`.
