# ADR 0002: локальные аккаунты, сессии и пары

Статус: реализовано для этапа авторизации. Дата: 17 ноября 2026 года.

## Область изменения

Реализован контракт `docs/AUTH_CONTRACT.md`: первый администратор через локальную CLI, вход, обновление и завершение сессии, создание и отключение аккаунтов, сброс паролей и связывание людей в пары. HTTP-регистрации нет. Расчёт цикла и дневник в этот этап не входят. `/health` и `/api/message` сохраняют публичный технический и синтетический характер.

Новая миграция добавляет таблицы `users`, `sessions`, `refresh_tokens` и `pairs`. Данные и первоначальная демонстрационная запись прежней миграции сохраняются. Стандартных аккаунтов и паролей в миграциях нет.

## Пароли и вход

Пароли хешируются Argon2id v19 с `m=19456 KiB`, `t=2`, `p=1` и индивидуальной случайной солью. Допустимы 12–128 символов и не более 512 байтов UTF-8; пароль не обрезается и не нормализуется. `username` одинаково при создании и входе очищается от внешних пробелов и приводится к ASCII lowercase, после чего проверяется диапазон 3–64 и набор `[a-z0-9_.-]`. Отображаемое имя содержит 1–80 символов без управляющих знаков.

Неизвестный пользователь и неверный пароль дают `invalid_credentials`. Для неизвестного пользователя выполняется Argon2-проверка синтетического PHC-хеша с теми же параметрами. Дорогие вычисления выполняются через `spawn_blocking`; семафор допускает два одновременных вычисления на экземпляр API и возвращает `rate_limited` при исчерпании.

Вход ограничен пятью попытками на нормализованное имя и 60 попытками суммарно за скользящую минуту на процесс. Записи ограничителя очищаются по этому окну, число имён ограничено суммарной квотой. IP-заголовкам reverse proxy не доверяют. После перезапуска ограничитель сбрасывается; для нескольких экземпляров или публичной установки понадобится общий ограничитель или настройка входного proxy.

JSON авторизации и управления ограничен 8192 байтами. Некорректные и слишком большие JSON-запросы получают `invalid_input`. Неизвестные поля входных моделей отклоняются, включая попытку менять роль через PATCH пользователя.

## Access JWT и актуальные полномочия

Access JWT подписывается только HS256 и имеет срок до 900 секунд. Проверяются подпись, фиксированные issuer `open-source-flo`, audience `flo-clients`, `exp`, `iat`, UUID пользователя и сессии. Допуск после истечения не применяется.

JWT не является единственным источником прав. Каждый защищённый запрос дополнительно проверяет в SQLite существование активного пользователя, неотозванную сессию и срок её действия. Роль берётся из текущей записи пользователя. Отключение аккаунта, logout и сброс пароля прекращают доступ по уже выпущенным access JWT немедленно для следующих проверок.

`Authorization: Bearer` имеет приоритет над cookie. Ошибочный, дублированный или некорректный Authorization не приводит к попытке использовать cookie. Пароли, хеши и токены в ответах пользователей и пар отсутствуют; access и native refresh выдаются только в ответах сессии по контракту.

## Refresh и отзыв

Refresh — случайные 32 байта из ОС, представленные 64 шестнадцатеричными символами. В БД сохраняется только SHA-256 хеш, связанный с сессией. Срок сессии абсолютный: семь дней с момента входа, без бесконечного продления при refresh. Access ограничивается также окончанием этого срока; `expires_in` может стать меньше 900 секунд перед завершением семи дней.

Обновление выполняется в SQLite-транзакции `BEGIN IMMEDIATE`: старый refresh отмечается использованным, создаётся новый, счётчик увеличивается. Хеши всей истории сессии сохраняются, поэтому обнаруживается повтор не только последнего, но и более раннего refresh. Любой такой replay отзывает всю сессию, включая новый access и refresh. Из двух конкурентных обновлений одним токеном одно может успеть получить ответ 200, второе получает 401 и отзывает семью. Клиенты должны сериализовать refresh.

Число ротаций ограничено 2048 на одну сессию. При превышении требуется новый вход. Сессии с истёкшими семью днями и их refresh-история удаляются каскадно при следующем успешном входе. Одновременно сохраняются не более 32 неотозванных сессий пользователя: перед новой сессией старые сверх лимита отзываются. Отозванная история сохраняется до окончания срока, чтобы поддерживать обнаружение replay. Это ограничивает рост истории и не требует фонового задания на текущем этапе.

Logout отзывает сессию и очищает обе cookie с теми же Path/SameSite/Secure-атрибутами. Для web действительный refresh позволяет завершить сессию и после истечения access. Native может передать access Bearer; для завершения по refresh без действительного access используется тело `{"client":"native","refresh_token":"..."}` без некорректного Authorization. Повторный web logout безопасно очищает cookie. Заголовок с неверным Bearer не переключается на cookie.

## Cookie и Origin

Web получает `flo_access` и `flo_refresh`: `HttpOnly`, `SameSite=Strict`, `Path=/api`, `Secure` по умолчанию. JSON web-ответа не содержит refresh. Native получает refresh в JSON. Все ответы известных auth/admin/me/setup маршрутов, включая ошибки, содержат `Cache-Control: no-store`.

Изменяющие запросы с cookie требуют точного Origin из `TRUSTED_ORIGINS`; отсутствие Origin и неподходящий Origin отклоняются. Web login также требует доверенный Origin. Native login/refresh с явно указанным client и без browser cookie/Origin допустим. Само поле `client=native` не отменяет проверку, если в запросе присутствует cookie или Origin. Для защищённых изменений без browser cookie допустим Bearer. CORS не включается.

`TRUSTED_ORIGINS` — список точных origins через запятую, без wildcard и путей. По умолчанию включены HTTP origins localhost/127.0.0.1 на портах 5173 и 8080. `COOKIE_SECURE=false` принимается только явно и только когда все доверенные origins указывают на loopback; для настоящих пользователей требуется HTTPS и соответствующий список origins.

## Ключ подписи

Настройки: `JWT_SECRET` либо `JWT_SECRET_FILE`, одновременно задавать их нельзя. Ключ содержит не менее 32 и не более 4096 байт; короткие и значения с низким разнообразием байтов отклоняются. Эта проверка не доказывает случайность произвольного пользовательского ключа; предпочтителен автоматически созданный случайный ключ.

Без настройки создаётся `.data/jwt.key`: случайные 32 байта, `create_new`, POSIX-права 0600. Ключ не меняется при следующем старте. Если `JWT_SECRET_FILE` указан и файла ещё нет, он создаётся с теми же правилами; в контейнере можно использовать `/data/jwt.key` на постоянном томе. Существующие ключи должны быть обычными файлами без прав group/other. Ключи и БД исключены из Git.

Сохранение БД без ключа приведёт к невозможности использовать старые JWT; ключ включается в защищённую резервную копию. Администратор сервера имеет доступ к хранилищу и памяти процесса; сквозное шифрование пользовательских данных этим решением не заявляется.

## Администратор и пары

Первый администратор создаётся командой:

```sh
cargo run --locked -p flo-api -- create-admin --username admin --display-name 'Администратор'
```

Пароль вводится скрыто с подтверждением. В автоматизированном локальном сценарии допускается `--password-stdin`; пароль не передаётся аргументом командной строки и не печатается. Тесты используют только синтетические значения и временную БД.

Bootstrap атомарно проверяет отсутствие любого admin, включая отключённого. Второй admin создаётся только авторизованным администратором через API. `/api/setup/status` использует тот же критерий; он возвращает только флаг. Сброс БД не используется как механизм восстановления доступа.

Роли `admin`, `tracker`, `partner` неизменяемы на этом этапе. Администратор создаёт аккаунты, отключает/включает их и сбрасывает пароль. Отключить самого себя через API нельзя. Проверка активной сессии администратора повторяется внутри write-транзакции, поэтому конкурентное взаимное отключение двух admin не оставляет установку без активного администратора. Сброс пароля и отключение отзывают все сессии пользователя. При отключении удаляется и его пара.

Пара связывает одного активного tracker и одного активного partner. Участники должны быть различны. Уникальные индексы и транзакция защищают от двойного участия при конкурентном создании; SQLite-trigger дополнительно проверяет роли и активность при вставке. Конфликт членства возвращает 409.

Администратор видит списки аккаунтов и пар. Обычный пользователь получает только свою пару и может прекратить её. Удаление выполняется по ID авторизованного пользователя, без возможности указать чужого участника. Последующие запросы обоих участников показывают `null`; прежняя связь не создаёт постоянного полномочия. Разрешения на чтение будущего дневника должны проверять актуальную связь на сервере. Уже скопированные вне приложения данные дистанционно удалить нельзя.

## Проверки

Добавлены интеграционные сценарии: отсутствие default admin, запрет повторного bootstrap, параметры PHC, неизвестный пользователь, неверный пароль, поддельные/истёкшие JWT, issuer/audience/алгоритм, Bearer без fallback, ротация и replay ранних refresh, конкурентный refresh, logout, cookie/Origin и защита от смены client, роли, изоляция пар, неверные роли и self-pair, конкурентное создание, разрыв связи, сброс пароля, отключение, защита self/последнего администратора, ограничение входов и JSON. Отдельно проверяются сохранность и права ключа. Прежние SQLite/message тесты сохранены.
