# Проверка архитектуры

Дата: 17 ноября 2026. Область: Rust API авторизации, административные операции, приглашения, Svelte-клиент и Kotlin Compose-клиент. Проверка исходников выполнена отдельно от реализации переключателя видимости паролей. Запуск на телефоне и внешний деплой не выполнялись.

## Вывод

Для текущего каркаса выбраны соразмерные технологии: один API, SQLite с миграциями, отдельные веб- и Android-клиенты. Клиентские HTTP-запросы централизованы; сервер проверяет роли, сессии и атомарность операций. В ходе проверки разделены HTTP-операции аккаунтов, сервисные правила и общие SQL-операции хранения. Часть работы с сессиями и приглашениями остаётся в существующих модулях; полная изоляция всех сценариев в рамках этой задачи не заявляется. По просмотренным участкам блокирующая ошибка авторизации не установлена; это ограниченное архитектурное ревью, не полный аудит безопасности.

## Границы слоёв

Веб: компонент отвечает за отображение и локальное состояние формы; модуль API — за HTTP, обновление сессии и проверку ответа; сервер — за окончательные разрешения и правила. Android: Compose → ViewModel → Repository → ApiTransport. Сервер: HTTP-извлечение и ответы → операции аккаунтов/пар/приглашений → SQL в рамках переданной транзакции.

Не требуется внедрять универсальный CRUD-фреймворк, generic repository, DI-контейнер или микросервисы. Общий код выделяется там, где совпадает правило или поведение. Формы регистрации по приглашению и создания аккаунта администратором имеют разные действия и не должны сливаться в компонент со множеством условных режимов только ради одинаковых полей.

## Проверка исправлений

Замечания переданы координатору до изменений. После согласования выполнен соразмерный рефакторинг:

- `accounts.rs` содержит HTTP-адаптеры списка, создания, изменения аккаунта и собственного пароля. `pairs.rs` содержит HTTP-операции пар.
- `account_service.rs` выполняет проверку бизнес-правил, управление транзакциями, создание и изменение аккаунта, защиту последнего администратора, проверку текущего пароля, удаление и создание пары. Операции аккаунтов используют SQL-методы `store.rs`.
- `store.rs` централизует чтение и запись аккаунтов, условную замену пароля, отзыв сессий и удаление/создание пар. Повторное создание пары администратором и по приглашению использует общий сервис. Пароль проверяется до захвата write lock; перед изменением сохранена проверка хеша внутри транзакции.
- Android: после удаления аккаунта вызывается `loadDashboard`; HTTP-транспорт и модели вынесены из репозитория. Общий `LoginForm` используется обычным входом и входом по приглашению; переключение видимости реализовано в общем `RetroField`.
- Веб: все поля пароля используют `PasswordField`; две операции выдачи приглашения используют общий `parseInvite`. При очистке поля пароля скрытое состояние восстанавливается.

Проверен итоговый исходный diff перечисленных участков. После последнего серверного изменения выполнены `cargo fmt --all`, `cargo test --locked --offline --workspace` (31 тест, все успешны) и `cargo clippy --locked --offline --workspace --all-targets -- -D warnings` (успешно). Публичные API, роли и миграции рефакторингом не менялись. Проверки клиентов выполняет координатор; здесь их успешность заранее не утверждается.

Остаются небольшие технические задачи: пакетная загрузка пользователей для списка пар вместо N+1; выделение JWT/session HTTP и crypto из `auth.rs` при следующем расширении; дальнейшее разделение сценариев приглашений и их SQL по мере роста. Наличие прямого SQL в небольших read-адаптерах пар и в существующих сценариях сессий описано явно. Внедрение отдельного слоя для каждого простого SELECT сейчас не требуется.

Блокирующих архитектурных замечаний для текущего функционала после исправлений не установлено. Наличие тестов и успешная сборка сами по себе не подтверждают удобство интерфейса на реальном устройстве.


## Проверки клиентского интерфейса

Координатор выполнил Svelte check (0 ошибок и предупреждений), 17 веб-тестов, production build, Android assembleDebug/lintDebug/testDebugUnitTest (18 JVM-тестов) после последнего изменения. Независимый проверяющий подтвердил сохранение ограничений и привязок во всех девяти веб-полях пароля; тела Android HTTP-транспорта и API-операций при переносе не менялись. Пароли и токены для проверки не брались из реальных аккаунтов.

В локальном браузере при ширине 390 px проверены показ/скрытие тестового текста, управление клавиатурой, сброс видимости после очистки и отсутствие горизонтального переполнения. После уточнения пользователя текстовая кнопка заменена встроенной иконкой: геометрия веб-поля до и после показа совпала (306 × 48 px, та же позиция). На Android иконка имеет фиксированную область 48 dp. Проверка Android на устройстве не выполнялась по указанию пользователя.

Modern Web Guidance установлен в проект; для форм прочитаны forms, autofill-sign-in-form, autofill-sign-up-form. Использованы type=button, aria-pressed, current-password/new-password, сохранение вставки и нативных ограничений. Рекомендации не изменяют текущую самостоятельную авторизацию или Y2K-дизайн.
