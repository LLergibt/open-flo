# Open-source-flo

Минимальный каркас самостоятельно развёртываемого приложения. Нативный Android-экран и веб-страница получают демонстрационный текст из SQLite через Rust API.

```text
Android (Kotlin / Compose) ──┐
                            ├── GET /api/message ── Rust / Axum ── SQLite
Web (Svelte / TypeScript) ───┘
```

На этом этапе реализована только проверка соединения. Дневник, прогнозы цикла, аккаунты, админка и партнёрский доступ ещё не реализованы. Тестовый API не требует авторизации и предназначен для синтетических данных. Лицензию публикации проекта предстоит выбрать до выпуска.

## Структура

```text
apps/android/       Android-проект для Android Studio
apps/web/           Веб-страница и manifest для standalone-отображения
crates/api/         API, встроенные миграции и интеграционные тесты
deploy/             Dockerfile и nginx для локального контейнерного запуска
scripts/            Команды запуска и проверки
docs/               Решения, правила работы агентов и результаты проверки
.codex/agents/      Пять согласованных профилей
```

Расчётное Rust-ядро и межплатформенные привязки будут добавлены вместе с алгоритмом. Для вывода демонстрационной строки они не требуются.

## Локальный запуск API и веба

Нужны Rust 1.91.1 или совместимый более новый, Node.js 26 и npm. Версии зависимостей зафиксированы в Cargo.lock и package-lock.json. При первой сборке требуется сеть для их загрузки.

```bash
cd /Users/georgijnazarov/projects/open-source-flo
./scripts/dev.sh
```

Скрипт установит npm-зависимости при их отсутствии и запустит оба сервиса. Первая сборка Rust может занять несколько минут.

- Веб: http://127.0.0.1:5173
- API: http://127.0.0.1:8080/api/message
- Проверка БД: http://127.0.0.1:8080/health
- База: `.data/flo.db`, игнорируется Git.
- Остановка обоих сервисов: Ctrl+C в терминале запуска.

Веб обращается к относительному `/api/message`. Vite проксирует запрос к API; разрешающий CORS не нужен. Нажатие «Обновить» повторяет запрос, не подставляя локальный текст вместо ошибки.

Переменные окружения и значения по умолчанию перечислены в `.env.example`. Этот файл служит примером; скрипты не исполняют и не загружают `.env` автоматически. Для другого адреса API задайте согласованные значения `BIND_ADDR` и `API_PROXY_TARGET` при запуске.

## Android Studio через Homebrew

```bash
brew install --cask android-studio
open -a "Android Studio"
```

Официальный cask: https://formulae.brew.sh/cask/android-studio

Пройдите Setup Wizard. В SDK Manager установите Android SDK Platform 35, Build-Tools 35.0.0, Platform-Tools, Android Emulator и ARM64-образ системы для Mac на Apple Silicon. В Device Manager создайте виртуальный телефон. Для этого каркаса NDK пока не нужен: он понадобится при подключении расчётного Rust-ядра к Android.

Откройте в Android Studio директорию:

```text
/Users/georgijnazarov/projects/open-source-flo/apps/android
```

Дождитесь Gradle Sync, выберите виртуальный телефон и нажмите Run. Пока приложение работает, API должен быть запущен на Mac. Внутри эмулятора адрес `10.0.2.2` соответствует Mac; `localhost` соответствует самому эмулятору.

Android-сборка использует JDK 17; зафиксированные версии Gradle и Android-плагина указаны в Android README. Если JDK из Android Studio несовместим с закреплённым Gradle, выберите JDK 17 в настройках Gradle JDK или укажите `JAVA_HOME`.

Для отдельной установки совместимого JDK:

```bash
brew install openjdk@17
export JAVA_HOME="$(brew --prefix openjdk@17)/libexec/openjdk.jdk/Contents/Home"
```

В Android Studio можно выбрать этот же JDK как Gradle JDK. Команда export действует в текущем терминале.

Сборка и установка из корня репозитория:

```bash
./scripts/android.sh assembleDebug
./scripts/android.sh installDebug
```

Скрипт использует заданный `JAVA_HOME`, а при его отсутствии пробует JDK 17 из стандартной установки Homebrew, затем JDK из Android Studio. Стандартный SDK на macOS определяется автоматически. Для иной установки задайте `ANDROID_HOME`.

Отладочное приложение использует `http://10.0.2.2:8080`. Для физического телефона нужен доступный ему адрес сервера; подробности настройки и ограничения HTTP перечислены в `apps/android/README.md`. Release-сборка требует явно заданный HTTPS URL API.

## Проверка источника данных

При работающем сервере в другом терминале:

```bash
curl --fail http://127.0.0.1:8080/api/message
```

Ожидаемый исходный ответ:

```json
{"message":"Привет из SQLite","source":"sqlite"}
```

Измените синтетическую строку непосредственно в БД через Python стандартной библиотеки:

```bash
cd /Users/georgijnazarov/projects/open-source-flo
python3 - <<'PY'
import sqlite3
with sqlite3.connect('.data/flo.db') as db:
    db.execute('UPDATE demo_messages SET message = ? WHERE id = ?',
               ('Новый текст из базы', 1))
PY
```

Нажмите обновление на обоих экранах. Они должны показать новый текст. Перезапуск API сохраняет изменение: начальная запись создаётся миграцией один раз. Удалять файл БД для обычного перезапуска не требуется.

## Проверки

После установки npm-зависимостей:

```bash
./scripts/check.sh
```

Выполняются форматирование Rust, интеграционные тесты API, проверка Svelte/TypeScript и сборка веба. Чтобы дополнительно собрать Android при готовых JDK/SDK:

```bash
CHECK_ANDROID=1 ./scripts/check.sh
```

Результаты фактически выполненных проверок и ограничения окружения сохраняются в `docs/TEST_REPORT.md`. Сборка APK не означает проверку на настоящем устройстве.

## Контейнерный запуск

При работающем Docker Engine и Docker Compose:

```bash
docker compose up --build
```

Если Compose установлен как отдельная команда Homebrew, используйте `docker-compose up --build`.

Открыть http://127.0.0.1:8088. nginx раздаёт веб и проксирует API на том же origin. SQLite хранится в именованном томе `flo-data`, отдельный процесс СУБД не нужен. Обычный `docker compose down` сохраняет том. `down -v` удаляет данные.

В контейнерном режиме Android должен обращаться к опубликованному порту 8088, например `http://10.0.2.2:8088` из эмулятора. Задайте URL через Gradle property согласно Android README. Нативный режим использует порт 8080.

Контейнерный порт по умолчанию доступен только с этого компьютера. Публичная установка, домен/IP, доверенные TLS-сертификаты, аутентификация и доступ из локальной сети настраиваются на следующем этапе; текущая конфигурация не является публичным медицинским сервисом.

## Веб на iPhone

Для первого просмотра на компьютере достаточно локального браузера. Показатели нативного поведения на iPhone проверяются отдельно после настройки доступного телефону HTTPS-адреса.

Сейчас подготовлен manifest для standalone-отображения. Service worker и офлайн-кеширование не реализованы: отсутствие сети должно показываться как ошибка соединения, а не как успешно полученные данные.

## Локальные инструменты проекта

Проект находится в `/Users/georgijnazarov/projects/open-source-flo`. Подготовленные JDK, SDK, Gradle, Cargo и npm cache перенесены в игнорируемую `.tooling/`. Скрипты dev/check/android подключают scripts/tooling.sh и автоматически используют эти инструменты, если соответствующие переменные окружения не заданы явно. Папка Codex для запуска и сборки больше не нужна.

Запуск из новой папки:

```bash
cd /Users/georgijnazarov/projects/open-source-flo
./scripts/dev.sh
```

Для подключённого телефона через USB:

```bash
.tooling/android-sdk/platform-tools/adb -d reverse tcp:8080 tcp:8080
./scripts/android.sh assembleDebug -PAPI_BASE_URL=http://127.0.0.1:8080
```

Локальные APK и снимки проверки сохраняются в `artifacts/`, которая исключена из Git и Docker-контекста.
