# Open Flo

Самостоятельно развёртываемое приложение: Rust API, SQLite, веб/PWA на Svelte и нативный Android на Kotlin/Compose. Реализованы JWT-авторизация, управление аккаунтами и связывание людей в пары через админку.

Администратор создаёт аккаунты с ролями «Администратор», «Владелец дневника» и «Партнёр». В пару связываются активный владелец дневника и активный партнёр. Участник видит только свою пару и может прекратить связь. Один аккаунт состоит максимум в одной активной паре. Расчёты менструального цикла, дневник и просмотр симптомов — следующие этапы; интерфейс не показывает выдуманные медицинские данные.

## Первый запуск

Для локальной разработки нужны Rust 1.91.1 или совместимый более новый, Node.js 26/npm. Android требует JDK 17 и SDK 35. Подготовленные локальные инструменты в `.tooling/` автоматически подключаются скриптами; они не входят в Git. В чистом клоне используются установленное окружение и Gradle Wrapper.

Проект находится в `/Users/georgijnazarov/projects/open-source-flo`.

Создать первого администратора:

```bash
cd /Users/georgijnazarov/projects/open-source-flo
./scripts/create-admin.sh
```

Пароль вводится скрыто и подтверждается повторно. Допустимо 12–128 символов; стандартного пароля нет. Команда предназначена только для первого администратора установки. Остальные аккаунты создаются в админке. Пароль не передаётся аргументом команды и не записывается в Git.

Запустить API и веб:

```bash
./scripts/dev.sh
```

- Веб: http://127.0.0.1:5173
- API: http://127.0.0.1:8080
- Проверка подключения к БД: http://127.0.0.1:8080/health
- Остановка: Ctrl+C в терминале запуска.

Скрипт ждёт готовности API до старта веба. Войти под созданным администратором, создать два аккаунта с ролями владельца дневника и партнёра, затем связать их в разделе пар. Для проверки участника выйти из администратора и войти под созданным аккаунтом.

## Сессии и права

- Пароли хешируются Argon2id с индивидуальной солью.
- Access JWT действует 15 минут. Подпись, алгоритм, срок, issuer и audience проверяются сервером.
- Сессия и активность аккаунта дополнительно проверяются в БД. Выход, блокировка и смена пароля отзывают доступ.
- Refresh-токены случайные, ротируются, в БД хранятся только хеши. Повторное использование старого токена отзывает сессию. Максимальная длительность сессии — 7 дней.
- Веб использует HttpOnly SameSite=Strict cookies и проверку Origin на изменяющих запросах. Токены не пишутся в localStorage или sessionStorage.
- Android передаёт JWT через Bearer и хранит токены только в памяти. После перезапуска приложения требуется вход. Проверка на телефоне на этом этапе не проводилась.
- Административные действия защищены API независимо от видимости кнопок. Разрыв пары прекращает разрешённое последующее получение данных; копии, ранее сохранённые вне приложения, удалённо отозвать нельзя.

Контракт маршрутов: `docs/AUTH_CONTRACT.md`. Решения и ограничения: `docs/adr/`.

## Конфигурация и сохранность

Файлы `.env.example` служат примерами. Нативные скрипты не исполняют `.env` автоматически; значения задаются переменными окружения.

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | SQLite; локально `sqlite://.data/flo.db` |
| `BIND_ADDR` | По умолчанию `127.0.0.1:8080` |
| `JWT_SECRET_FILE` | Файл ключа; по умолчанию `.data/jwt.key` |
| `JWT_SECRET` | Альтернатива файлу: случайный ключ минимум 32 байта; не задавать обе переменные одновременно |
| `COOKIE_SECURE` | По умолчанию `true`; локальный dev-скрипт явно задаёт `false` |
| `TRUSTED_ORIGINS` | Точные разрешённые origins без wildcard; dev-скрипт задаёт localhost/127.0.0.1:5173 |
| `API_PROXY_TARGET` | Адрес API для веб-прокси, локально `http://127.0.0.1:8080` |

Новые каталоги данных и файлы SQLite создаются с закрытыми правами на Unix. Для существующей установки с отдельной папкой `.data` проверьте и при необходимости ограничьте права:

```bash
chmod 700 .data
find .data -maxdepth 1 -type f -exec chmod 600 {} +
```

Произвольные существующие БД по `DATABASE_URL` автоматически не переоформляются: их доступ настраивает владелец сервера.

Если ключ не задан, сервер создаёт случайный ключ в файле с закрытыми правами. Не удаляйте ключ для обычного перезапуска. Резервное копирование должно учитывать БД и ключ; их нужно хранить отдельно от исходников и защищать доступ к копиям. Изменение ключа делает выпущенные JWT недействительными.

Локальные HTTP-настройки предназначены для разработки. Для публичной установки с паролями используйте HTTPS, Secure cookies и собственный точный `TRUSTED_ORIGINS`. Пользовательские данные, пароли, JWT, refresh-токены и ключи не должны попадать в логи или аналитические сервисы.

## Android без Android Studio

При готовых JDK/SDK:

```bash
./scripts/android.sh assembleDebug -PAPI_BASE_URL=http://127.0.0.1:8080
```

Скрипт сначала использует явные переменные окружения, затем подготовленные инструменты проекта и доступные системные установки. Подробности Android Studio, SDK и закреплённых версий — в `apps/android/README.md`.

Отладочный HTTP разрешён только в debug; release требует явно заданного HTTPS URL. Распространение и release signing пока не настроены. `.tooling/`, `.data/`, APK, ключи и `artifacts/` исключены из Git.

## Проверки без телефона

```bash
./scripts/check.sh
python3 scripts/smoke-auth.py
```

HTTP smoke требует собранного `flo-api`; по умолчанию ищет `.tooling/target/debug/flo-api`. Для чистого клона:

```bash
cargo build --locked -p flo-api
FLO_API_BIN="$PWD/target/debug/flo-api" python3 scripts/smoke-auth.py
```

Проверка создаёт временные синтетические аккаунты и БД, запускает собственный loopback-сервер и останавливает его после завершения. Реальные аккаунты установки не затрагиваются.

Для сборки Android:

```bash
CHECK_ANDROID=1 ./scripts/check.sh
```

Отдельные отчёты в `docs/` различают автоматические проверки, браузерную проверку и ограничения. Сборка APK не означает запуск на устройстве. Телефон на этапе авторизации не используется.

## Контейнеры

При работающем Docker Engine:

```bash
COOKIE_SECURE=false docker compose up --build
```

Эта команда предназначена для локальной проверки на http://127.0.0.1:8088. При standalone Compose используйте `docker-compose`.

Первый администратор внутри контейнера:

```bash
docker compose exec api flo-api create-admin --username root --display-name root
```

SQLite и ключ JWT сохраняются в томе `flo-data` (`/data/flo.db`, `/data/jwt.key`). Обычный `docker compose down` сохраняет том; `down -v` удаляет данные. Для публичной установки нужны HTTPS и собственный origin; текущий шаблон публикует порт только на loopback. Контейнерные сборки требуют отдельной проверки при доступном Docker daemon.

## Текущий объём

Веб сохраняет manifest standalone, но автономный режим и service worker ещё не реализованы. API `/api/message` остаётся публичным техническим маршрутом с синтетическим текстом; реальные записи аккаунтов через него не выдаются. Лицензию публикации предстоит выбрать отдельно. Расчёты цикла и медицинские прогнозы не реализованы.

### Приглашение партнёра и пароль

Скрипт `./scripts/create-admin.sh` по умолчанию создаёт администратора с логином и именем `root`. Пароль задаётся интерактивно; существующие аккаунты не переименовываются.

Владелец дневника создаёт ссылку в своём профиле. Партнёр открывает её в вебе или вставляет ссылку/код в Android. Можно зарегистрировать новый аккаунт партнёра либо войти в существующий и явно подтвердить привязку. Ссылка одноразовая, действует 24 часа; новая ссылка отменяет предыдущую. Просмотр приглашения не создаёт пару.

Для Android и отправки ссылок задайте `PUBLIC_APP_URL` — доступный партнёру HTTPS-адрес веб-приложения без завершающего слеша. Для локальной разработки разрешён HTTP loopback. В dev-скрипте используется `http://127.0.0.1:5173`; этот адрес доступен только на самом компьютере. Веб может собрать ссылку из текущего адреса, если настройка не задана.

Все роли могут сменить пароль в профиле, указав текущий пароль. Успешная смена завершает все сессии аккаунта и отзывает его незавершённое приглашение. После этого нужно войти снова.

Удаление аккаунта доступно в профиле с подтверждением текущего пароля и в админке для других аккаунтов. Удаляются аккаунт, его сессии, refresh-токены, незавершённое приглашение и пара; аккаунт партнёра сохраняется. Последний активный администратор защищён от удаления. Резервные копии БД этим действием не очищаются.

В админке доступны одноразовые ссылки регистрации без пары для ролей «Владелец дневника» и «Партнёр». Роль закреплена на сервере; создать администратора по ссылке нельзя. Для каждого администратора сохраняется одна ссылка на роль: новая заменяет предыдущую для той же роли. Срок — 24 часа; ссылку можно отозвать. Отключение, удаление администратора или смена его пароля отзывает выданные им ссылки.


## Рекомендации для веб-разработки

В проект установлен [Modern Web Guidance](https://github.com/GoogleChrome/modern-web-guidance) командой `npx modern-web-guidance@latest install`. Навык находится в `.agents/skills/modern-web-guidance/`, источник закреплён в `skills-lock.json`. Он не входит в runtime-зависимости веба. Правила дальнейшего использования находятся в AGENTS.md.

Пример поиска рекомендаций с проектным кешем:

```bash
DISABLE_TELEMETRY=1 npm_config_cache="$PWD/.tooling/npm-cache" npx --yes modern-web-guidance@latest search "password visibility toggle"
```

Все веб-поля пароля используют `PasswordField.svelte`: иконка глаза внутри поля имеет постоянную область нажатия, сохраняются автозаполнение и нативная валидация. На Android аналогичное поведение реализовано в `RetroField.kt`; обычный вход и вход по приглашению используют общую `LoginForm.kt`. Бизнес-правила аккаунтов API находятся в `account_service.rs`, SQL-операции — в `store.rs`, HTTP-обработчики аккаунтов — в `accounts.rs`. Итоги и ограничения ревью: `docs/ARCHITECTURE_REVIEW.md`.
